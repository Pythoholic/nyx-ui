# Nyx UI v0.2 Priority 1 scoping notes

Status: scoping only; no implementation has been performed.  
Date: 2026-09-17

## Recommendation

Treat v0.2 as a sequence of composable primitives, not a flat checklist. Land the static vocabulary first, then a small internal interaction substrate, then build the larger widgets by composition. In particular, share positioning, dismissal, roving focus, and typeahead mechanics where appropriate, but do **not** merge menu, listbox, and navigation semantics into one controller: their ARIA roles and keyboard behavior differ.

Before multiplying examples, also resolve the architecture requirement that registry and docs render one canonical source. They currently contain separately maintained markup. Otherwise every Priority 1 addition creates immediate drift.

## Proposed build order

1. **Harden the plugin contract and test harness.** Standardize idempotent `initX(root)`, explicit constructors, `destroy()`, typed events, state/ARIA synchronization, and re-initialization after destroy. Decide whether an initializer includes `root` itself as well as descendants. Add interaction/accessibility tests before adding many modules. Address dialog stacking/scroll-lock ownership and configurable initial focus/light dismissal because Alert Dialog and Command Palette depend on them. Toast currently does not meet the same lifecycle/event shape as Dialog and Tabs.

2. **Ship the static semantic primitives.** Add Avatar/Avatar Group, Card/Item/List/List Group, Separator/Divider, and Kbd. These require CSS and canonical registry markup, not plugin classes. Keep their HTML semantic: `img`, lists, `article`/`section` where appropriate, `hr`, and `kbd`.

3. **Normalize Toggle and Toggle Group.** Reuse the existing button, button-group, and segmented-control styling. A single toggle is a native `button` with `aria-pressed`; an exclusive form choice is native radio inputs/`fieldset`; multi-select toggles are pressed buttons or checkboxes. Add JS only where Nyx promises state ownership or roving focus.

4. **Add the shared overlay substrate and Dropdown Menu.** Install `@floating-ui/dom` once in `@nyx-ui/plugins` and keep its imports inside the modules that position overlays. Internal helpers should cover `computePosition`/`autoUpdate`, offset/flip/shift/size middleware, outside interaction, Escape dismissal, focus return, item discovery, roving focus, and typeahead. The Dropdown module should combine the HTML Popover API for top-layer/open state where supported with Floating UI for geometry; it must define disabled items, separators, check/radio items, submenus, and close-on-select behavior before dependent menu components land.

5. **Build menu derivatives without conflating semantics.** Context Menu can reuse Dropdown's menu behavior plus a Floating UI virtual reference at pointer/keyboard coordinates. Menubar can reuse menu-item navigation and floating submenus, but needs its own horizontal root-keyboard contract. Navigation Menu should remain semantic `nav` with links and disclosure/flyout behavior; it must not use `role="menubar"` unless it truly represents application commands.

6. **Extend Dialog, then publish Alert Dialog as a composition.** Use the existing native `<dialog>` controller rather than a separate modal primitive. Add data/options for initial focus and whether Escape/backdrop may dismiss. An Alert Dialog registry pattern can set `role="alertdialog"`, label/description relationships, destructive/cancel actions, and safe initial focus. A separate `NyxAlertDialog` class/export is unnecessary unless it gains behavior that cannot live as Dialog options.

7. **Build Combobox, then Searchable Select.** Retain native `<select>` for ordinary choices. The enhanced component should implement the ARIA combobox/listbox pattern, filtering, active option, selection, keyboard behavior, and form value synchronization. It may reuse low-level typeahead/navigation and overlay helpers, but not menu roles or menu-specific selection behavior. Searchable Select should be a documented Combobox configuration rather than a second engine.

8. **Build Command Palette by composition.** Compose the hardened Dialog with a search input and listbox/command-result controller. Reuse filtering and active-descendant utilities from Combobox where their contracts match. A centered modal palette needs no Floating UI.

9. **Mature the existing app shell into Sidebar.** Preserve `aside`/`nav` landmarks and add a controller for expanded/collapsed state, `aria-expanded`/`aria-controls`, optional persistence, and responsive state changes. On small screens, compose the existing dialog drawer behavior if the sidebar becomes modal; do not create another Sheet/Drawer primitive.

10. **Add the smaller form behaviors.** Prefer one native OTP input where possible; offer a multi-cell PIN controller only as an enhanced variant. Mature the existing file input/drop-zone markup with validation, drag/drop, preview lifecycle, progress display, and events, while leaving network transport to a consumer callback/adapter.

11. **Add Calendar, then Date Picker.** First define a standalone, keyboard-complete calendar grid and its date/value model. Date Picker then composes that calendar with an input and positioned popover. For simple cases, use Nyx-styled native date and time inputs: Nyx owns the closed control surface, while the platform still owns the picker, keyboard behavior, constraint validation, and mobile input mode.

12. **Mature Table into Advanced Data Table.** Keep semantic table markup and layer on sortable header buttons, filter controls, checkbox selection, and the existing pagination styles. Define client-controlled and server-controlled modes before the API is frozen; keep fetching, virtualization, and a general grid/spreadsheet engine out of the initial scope.

Each step should update the canonical registry source, docs rendering, per-component ESM export where behavior exists, keyboard documentation, and focused interaction/accessibility tests together.

`@floating-ui/dom` should be a single runtime dependency of `@nyx-ui/plugins`, never of core. Only the relevant ESM modules should import it, so Dialog/Tabs/Toast and static components do not bundle positioning code. Tooltip and generic Popover can use the same helper later, but their maturation need not expand this milestone unless explicitly added.

## Existing coverage: mature instead of duplicate

- **Drawer/Sheet:** already a Dialog layout (`data-layout="drawer"`); keep one controller.
- **Alert Dialog:** a constrained Dialog composition, not a second modal implementation.
- **Card:** `.nyx-panel`, `.nyx-media-card`, and `.nyx-batch-tile` already overlap. Introduce one generic card anatomy (or explicitly bless Panel as Card) and retain specialized compositions instead of parallel near-identical primitives.
- **Toggle Group:** `.nyx-button-group` provides grouping geometry and `.nyx-segmented` already provides a native-radio exclusive choice. Correct and document their semantics before adding another visual system. The current button-group demo also needs complete `aria-pressed="true|false"` state management if it is presented as a toggle group.
- **Searchable Select:** make it a Combobox mode; retain the current native Select as the recommended non-searchable control.
- **File Upload:** mature `.nyx-file` and its existing native input rather than adding a second upload surface.
- **Advanced Data Table:** mature `.nyx-table` and reuse `.nyx-pagination`; do not introduce a separate grid unless editable/spreadsheet interaction is explicitly requested.
- **Sidebar:** mature `.nyx-app-shell`/`.nyx-app-sidebar`; compose the existing drawer mode for modal mobile presentation.
- **Date Picker:** retain the native date and time elements alongside the custom picker, but present their closed surfaces with Nyx control styling rather than unmodified platform chrome.

## Native date and time appearance decision (2026-09-19)

The earlier recommendation to use an unmodified native date input as the visual default is reversed. Native date and time elements remain the semantic and behavioral default for simple cases, but their closed control surfaces now use Nyx border, height, background, typography, focus, and picker-indicator styling so they sit consistently beside other controls. Nyx does not replace the platform picker popup or intercept its keyboard, validation, or mobile behavior.

## Motion application rule (2026-09-19)

Motion explains a state change; it does not decorate a resting interface. Use the existing duration, easing, and keyframe vocabulary in this order:

- Visibility changes animate when spatial context would otherwise be lost: overlays and modal surfaces enter and exit, with drawers preserving their direction of travel.
- Pressed, selected, checked, expanded, and progress states use short transitions on the property that changed. Do not animate unrelated descendants.
- Items added to a generated list fade in; dismissed queue or notification items slide out and become immediately inert and absent from the component's value before physical removal; reordered table rows use a short fade to re-establish reading order.
- Loading motion runs only while work is active. Spinners, indeterminate progress, skeletons, and active queue signals stop when the corresponding state ends.
- Ambient or repeated motion without a state-signalling purpose is out of scope.

The single reduced-motion rule in `packages/core/src/motion.css` applies to component CSS and utility classes alike. Do not add per-component media queries; new motion must continue to inherit that global duration and iteration override.

## Decisions required before implementation

1. **Release breadth:** this list contains several product-sized widgets. Recommend labeling static primitives and the menu foundation stable first, while Calendar/Date Picker and Advanced Data Table enter v0.2 as preview components unless the milestone can absorb their accessibility and test burden.
2. **Browser floor:** the deferred browser matrix now blocks decisions around `<dialog>`, Popover API, `inert`, and mobile behavior. Set the supported browser versions and polyfill policy first.
3. **Canonical-source mechanism:** decide how registry HTML is imported/rendered by the docs before adding more duplicated template strings.
4. **Ownership model:** decide whether Combobox, Calendar, Sidebar, and Table are uncontrolled DOM owners, controlled event emitters, or support both. Public event names, cancellation, and value synchronization depend on this.
5. **Menu taxonomy:** confirm that Menubar means desktop application commands and Navigation Menu means site/product navigation. They should not be aliases.
6. **Calendar scope:** specify single date versus range/multiple selection, locale/week start, disabled dates, min/max, and time-zone expectations. The architecture says calendars should be styled adapters/examples rather than dependencies of core; a full calendar engine in plugins would be a deliberate clarification of that boundary.
7. **Upload boundary:** confirm that Nyx owns selection/validation/previews and exposes progress/events, while the consumer owns the actual upload request. Browser-native upload progress is transport-dependent; `fetch` does not provide a universally useful upload-progress callback.
8. **Table boundary:** specify client versus server sorting/filtering/pagination, comparator/filter hooks, selection persistence across pages, and whether virtualization is explicitly out of scope.
9. **Sidebar behavior:** specify desktop rail versus fully hidden collapse, mobile modal breakpoint, persistence key/opt-in behavior, and whether responsive changes follow CSS/media queries or application control.
10. **OTP ergonomics:** confirm whether the visual requirement truly needs multiple inputs. A single native input is more robust for paste, password managers, autofill, and screen readers; never use `type="number"` for codes because leading zeroes and `maxlength` behavior are wrong for this use.

No additional runtime library is justified by the current scope. In particular, date, table, upload, focus, or command-palette libraries should not be added without a separate architecture decision.
